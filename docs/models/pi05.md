# pi0.5 (flow matching with an action expert), DROID joint-position weights

Reference sheet for the `pi05` model of `tactile-vla-rl`: what goes in, what comes out, what the network is made of, how it is
fine-tuned (full or LoRA), and what is parameterised in `configs/model/pi05.yaml`.

Everything below was read in the pinned openpi fork (`third_party/openpi`, commit `f7cfe2d2`, the same commit as expo-ft) or measured on
it. Parameter counts come from `jax.eval_shape` on the real openpi configs (no weights loaded, no GPU needed). What is a consequence
drawn from those facts rather than a fact is said so. What was not checked is in the last section.

## 1. At a glance

| | |
|---|---|
| Family | pi0.5 (`Pi0Config(pi05=True)`), generative: **flow matching** (a continuous, diffusion-like model). Not autoregressive over actions |
| Backbone (VLM) | PaliGemma: **SigLIP So400m/14** vision tower + **Gemma 2B** language model |
| Action head | **action expert**: a second, smaller Gemma-style transformer (width 1024) that denoises the action chunk |
| Weights used | `gs://openpi-assets/checkpoints/pi05_droid_jointpos` (`params/` and `assets/` with the DROID normalisation statistics) |
| Parameters | 3.35 G without LoRA, 3.40 G with LoRA on both components (sections 2 and 6) |
| Input | 2 camera images (224×224), joint state (7) + gripper (1) written **as text tokens**, a language prompt |
| Output | a chunk of **16** steps × 8 values (7 joint **offsets** from the chunk-start state + gripper), natively 32 dimensions of which 8 are read |
| Sampling | Euler integration of the learned velocity field, **10** steps by default, from Gaussian noise |
| Training loss | flow-matching mean squared error on the velocity |
| Default LoRA | rank **16** on the VLM (`gemma_2b_lora`), rank **32** on the action expert (`gemma_300m_lora`) |
| openpi config used for data and norm stats | `expo_pi05_droid_lora_finetune_sft_joint_state` |
| Our files | `configs/model/pi05.yaml`, `src/models/` (`interface.py`, `settings.py`, `openpi_config.py`, `loading.py`, `openpi_policy.py`) |

## 2. Architecture

### 2.1 Components

| Component | Architecture | Parameters (measured) |
|---|---|---:|
| Vision tower | SigLIP So400m/14, 224×224 input, patch 14 → 16×16 = **256 tokens per image**, projected to the Gemma width (2048) | 414.8 M |
| VLM language model | Gemma 2B: 18 layers, width 2048, MLP 16 384, 8 heads, 1 KV head (multi-query), head dim 256, vocabulary 257 152 | 2508.5 M (of which the embedding table is 526.6 M) |
| Action expert | Gemma-style: 18 layers, width 1024, MLP 4096, 8 heads, 1 KV head, head dim 256 | 427.9 M (311.5 M transformer + 116.5 M adaRMSNorm modulation) |
| Action projections and time MLP | `action_in_proj` (32 → 1024), `time_mlp_in`, `time_mlp_out` (1024 → 1024), `action_out_proj` (1024 → 32) | 2.2 M |
| **Total, no LoRA** | | **3353.4 M** |

The "300M" in the name `gemma_300m` is nominal: 311.5 M without adaRMS, 427.9 M in pi0.5 because adaRMSNorm adds a modulation layer to
every normalisation (pi0, which has no adaRMS, has a 311.5 M expert). Weights are `bfloat16` (3.4 G parameters ≈ 6.8 GB).

### 2.2 How the two Gemmas work together

- The VLM and the action expert are **two sets of weights with joint attention**: at each of the 18 layers the queries, keys and values
  of both are concatenated and attended over together (`gemma.py`, `Attention`), then each token goes through its own expert's
  feed-forward. Both have 18 layers, 8 heads and head dim 256 for that reason.
- **Token layout and attention** (`pi0.py`, `make_attn_mask`):
  - *prefix* = image tokens, then the text tokens (prompt **and** state). Full bidirectional attention inside the prefix. The prefix never
    attends to the action tokens.
  - *suffix* = the 16 noisy-action tokens (one per chunk step). They attend to the whole prefix and bidirectionally to each other.
  - At inference the prefix is computed **once** and its key/value cache is reused by every denoising step: only the 16 action tokens
    are recomputed at each of the 10 steps.
- **The flow-matching time** `t` is embedded with a sine-cosine encoding (periods 4e-3 to 4.0), passed through `time_mlp_in` and
  `time_mlp_out` (swish after each), and injected into the action expert through **adaRMSNorm**: the normalisations of the expert
  are modulated by this vector. (pi0 instead concatenates the time embedding to each action token and has a continuous state token;
  pi0.5 has neither.)

## 3. Observation space

### 3.1 What the environment sends and what the model reads

`src/models/interface.py` (`to_openpi_obs`) takes five things from the environment's observation dictionary
(`src/envs/protocol.py`) and ignores all the others:

| Environment key | Shape (one environment) | Model input |
|---|---|---|
| `observation/exterior_image_1_left` | (224, 224, 3) uint8 | image `base_0_rgb` |
| `observation/wrist_image_left` | (224, 224, 3) uint8 | image `left_wrist_0_rgb` |
| (none) | zeros | image `right_wrist_0_rgb`, **masked out** (`image_mask = False`) |
| `observation/joint_position` | (7,) float32, rad | state, dims 0 to 6 |
| `observation/gripper_position` | (1,) float32, 0 = open, 1 = closed | state, dim 7 |
| the `prompt` (`EnvSpec.prompt`, "Insert the peg into the socket.") | string | text |

Not read by the baseline: `extra/tactile` (2, 7, 4), `extra/ft_force`, `extra/gripper_effort`, `extra/force_threshold`,
`extra/peg_socket_offset`. They reach the model only when a component's `use_tactile` / `use_force` is switched on (section 9).

### 3.2 Processing (openpi `DroidInputs`, `ModelTransformFactory`)

1. **Images**: resized with padding to 224×224 (a no-op here), scaled to [-1, 1]. With `train=True` (our `loss(..., train=True)`),
   openpi's augmentation is applied: for the exterior image a random crop of 95 % (resized back) and a rotation of ±5°, for every image a
   colour jitter (brightness 0.3, contrast 0.4, saturation 0.5); the wrist image gets no geometric augmentation.
2. **State**: 8 values (7 joints + gripper), **normalised with quantiles** (q01/q99 of the DROID statistics, `use_quantile_norm` is on for every
   model but pi0), then **discretised into 256 bins over [-1, 1]** and written as integers in the prompt. The state is therefore *text*, not a
   continuous input.
3. **Prompt**: `"Task: <prompt>, State: <8 integers>;\nAction: "`, tokenised with the PaliGemma tokenizer. The prompt text is stripped and its
   `_` and newlines are replaced by spaces; it is **not** lower-cased.
4. **Token budget**: `max_token_len = 200` text tokens (pi0.5 default; a longer sequence is truncated with a warning). Sequence seen by the
   VLM: 3 × 256 = **768 image tokens** (the masked third image included) + at most 200 text tokens; the expert adds 16 action tokens.

## 4. Action space

| | |
|---|---|
| Native model output | `(action_horizon = 16, action_dim = 32)`; the state and actions are zero-padded to 32 (`PadStatesAndActions`) |
| Read by openpi's output transform | the first **8**: columns 0 to 6 = joints, column 7 = gripper (`DroidOutputs(action_dim=8)`) |
| Joints (0 to 6) | **offsets in rad from the joint state at the moment of the plan** (the chunk-start state), not from the current state: the 16 steps of a chunk all refer to the same state |
| Gripper (7) | **absolute** command, 0 = open, 1 = closed |
| Normalisation | the model works in quantile-normalised space (DROID statistics of the checkpoint's `assets/`); the output transform un-normalises |
| Chunk length in time | 16 steps; at the environment's 15 Hz control rate (DROID's rate) that is about 1.07 s. How many steps are executed before planning again is a choice of the algorithm, not of the model |

Conversion to the environment's action space (`chunk_to_targets`, `output_semantics: offsets_from_chunk_start_state` in the YAML): the
environment wants 7 **absolute** joint targets + gripper, so the state at the moment of the plan is **added back once** to columns 0 to 6.
`targets_to_chunk` is the inverse (a demonstration, in absolute targets, becomes offsets: this is exactly openpi's `DeltaActions`, which
`expo_pi05_droid_lora_finetune_sft_joint_state_delta` applies at training time only, with no `AbsoluteActions` on the output, so that the
state is added once and only by us). With `gripper_can_open: false` the environment ignores column 7.

## 5. Generation: flow matching

**Training** (`Pi0.compute_loss`): for an action chunk `a` (normalised, padded to 32), noise `ε ~ N(0, I)` and a time `t ~ Beta(1.5, 1)` rescaled
to [0.001, 1] (more weight on noisy times):

    x_t = t · ε + (1 − t) · a          target velocity  u = ε − a          loss = mean over the 32 dims of (v_θ(x_t, t, obs) − u)²

The loss is returned per chunk step; it averages **all 32 dimensions, the 24 padded ones included** (their target action is 0).

**Sampling** (`Pi0.sample_actions`, convention t = 1 is noise, t = 0 the data): start from `x = ε`, then `num_steps` (default **10**) Euler
steps `x ← x + dt · v_θ(x, t)` with `dt = −1/num_steps`. The sampler is a deterministic function of the noise: the only randomness of a chunk
is the initial noise. The pinned fork adds `num_samples`: S independent noises per observation sharing one prefix computation. Our
`OpenPIPolicy.plan(..., num_samples=S)` uses it, so S samples cost one prefix pass and S × 10 expert passes.

## 6. Where the LoRA is, and what is trained

### 6.1 The LoRA of openpi (not modified by us)

- Applied, in **every one of the 18 layers**, to the attention projections (q, k/v, output) and to the feed-forward matrices (gating and
  linear), of the **VLM Gemma** and/or of the **action expert**, independently (`gemma.py`: `gemma_2b_lora`, `gemma_300m_lora`).
- `W + (alpha / rank) · A·B`, with **alpha = rank** in openpi's variants (scaling 1.0); no rank-stabilised variant (`rslora = False`).
- **Initialisation: normal(0, 0.01) for both `lora_a` and `lora_b`** (the LoRA paper starts from B = 0). A freshly initialised LoRA model is
  therefore the base model plus a small random perturbation (measured on 2026-11-10: about 1 % of the chunk on real observations), not exactly
  the base function. `use_lora: false` everywhere is the exact base function.
- **Default ranks**: 16 on the VLM, 32 on the action expert.

### 6.2 What is trainable (`Pi0Config.get_freeze_filter`, openpi's own filter)

The filter freezes the Gemma weights of a component **only if that component has LoRA**, and always lets the LoRA matrices train. It does
**not** touch the vision tower or the action projections: they train in every configuration.

| `vlm.use_lora` | `action_head.use_lora` | Trainable | Parameters trained | Total parameters |
|:--:|:--:|---|---:|---:|
| true | true | LoRA (both) + SigLIP + projections / time MLP | **467.0 M** (13.7 %) | 3403.4 M |
| true | false | LoRA (VLM) + **the whole action expert** + SigLIP + projections | 872.8 M | 3381.3 M |
| false | true | **the whole VLM** + LoRA (expert) + SigLIP + projections | 2947.6 M | 3375.6 M |
| false | false | everything (full fine-tuning) | **3353.4 M** | 3353.4 M |

Breakdown of the default (LoRA on both): LoRA VLM 27.9 M + LoRA expert 22.1 M + SigLIP 414.8 M + projections 2.2 M = 467.0 M; frozen: Gemma VLM
2508.5 M + Gemma expert 427.9 M.

### 6.3 Changing the rank

`lora_rank` in the component block of the YAML (or `--set vlm.lora_rank=8`). The LoRA parameters are **linear in the rank**
(1.74 M per unit of rank on the VLM, 0.69 M on the action expert; derived from the two measured points, not re-measured):

| Rank | 4 | 8 | 16 | 32 | 64 |
|---|---:|---:|---:|---:|---:|
| LoRA VLM (M) | 7.0 | 14.0 | **27.9** | 55.8 | 111.6 |
| LoRA action expert (M) | 2.8 | 5.5 | 11.1 | **22.1** | 44.2 |

Another rank changes the structure of the model: a checkpoint trained with a rank must be loaded with the same one. The default ranks give
exactly openpi's variants; another rank is built by `src/models/openpi_config.py` as `gemma_*_lora_r<rank>` (same LoRA, `alpha = rank`; the
fork is not modified).

### 6.4 Full fine-tuning

`use_lora: false` in both blocks (`--set vlm.use_lora=false --set action_head.use_lora=false`). 3.35 G trainable parameters; the optimiser
state (two moments per parameter) is what makes this expensive, which is why the full fine-tuning has its own job on an A100 80 GB while the
LoRA experiments run on an L40S. Memory was not measured here.

## 7. Loading the weights

The checkpoint **has no LoRA tensors**, so openpi's strict loading fails when LoRA is on (`symmetric difference of key sets:
{'lora_a', 'lora_b'}`). `load: weight_loader` (`src/models/loading.py`) does what expo-ft does: the checkpoint weights, plus the LoRA
parameters taken from the model's own initialisation (normal(0.01), section 6.1), everything in `bfloat16`. `load: strict` is possible only with no
LoRA anywhere. The norm statistics are read from the checkpoint's `assets/` (asset id `droid`) unless the model YAML has a `norm_stats` block (`dir`, `asset_id`), as for the SFT on the FORGE demonstrations (`docs/algos/sft.md`, section 2b).

## 8. Fine-tuning defaults of the openpi configs we start from

`expo_pi05_droid_lora_finetune_sft_joint_state` and its `_delta` variant (for datasets whose actions are absolute joint targets, as ours):
`Pi0Config(pi05=True, action_dim=32, action_horizon=16, gemma_2b_lora, gemma_300m_lora)`, learning rate 2.5e-5 (cosine schedule whose end value
equals its peak: constant), no warm-up, batch 64, 20 000 steps nominal, no EMA, `prompt_from_task=True`. These are the starting values of the SFT
of expo-ft (which ran it for far fewer steps on its demonstrations), not the recipe of the released checkpoint, which is not in this repo.

## 9. Where touch can enter (nothing is implemented yet)

`configs/model/pi05.yaml` has one block per component, `vlm` and `action_head`, each with `use_tactile`, `use_force` and `force_mode`
(all off: this is the task-only baseline). A component that asks for touch stops with an explicit error until an injection exists
(`src/touch/injection`). What the architecture offers, as facts about the model and not as decisions:

- the state is already **text** in the prefix: a touch vector could be discretised into the prompt like the joints (VLM side);
- the action expert takes **continuous** tokens: a touch vector could be projected to the expert width and added to the suffix (action-head
  side), as pi0 does with its state token;
- the injection can be trained in LoRA mode (new projection trainable, Gemma weights frozen) or in full fine-tuning.

## 10. What it means for reinforcement learning (consequences, not openpi facts)

- A chunk is a deterministic function of the initial noise: the policy's stochasticity is the noise, and the **log-likelihood of a chunk is
  not a closed-form product of probabilities** as for a token model. RL on this model needs either an algorithm that does not require
  the likelihood, or a stochastic denoising chain.
- Sampling costs 10 expert passes after one prefix pass; the 768 image tokens dominate the prefix.
- The trainable set is large even in LoRA mode (467 M) because the vision tower is not frozen by openpi's filter.
